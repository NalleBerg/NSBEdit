================================================================================
  NSBEdit - AI Shell Internals (ollama_ai.cpp / ollama_ai.h)
================================================================================

  This note covers the standalone AI shell window that was extracted from
  NSBEdit.cpp into ollama_ai.cpp / ollama_ai.h.

FILES:
  ollama_ai.h                 Public entry point: Ne_ShowAiWindow(HWND parent)
  ollama_ai.cpp               Window class, menu logic, layout, owner-draw UI
  ne_ai_bootstrap.h/.cpp      Loads persisted AI bootstrap settings
  ne_ai_client.h/.cpp         Probes Ollama localhost availability and streams
                              reply chunks through the curl-backed transport

================================================================================
1. PURPOSE
================================================================================

  The AI shell is a separate top-level window owned by the main editor.
  It provides a lightweight local/cloud control surface for the current AI
  feature set without keeping the implementation inside NSBEdit.cpp.

  Current responsibilities:
    - Open and reuse the AI window.
    - Show current model, fallback model, cloud/local state, and sign-in state.
    - Offer menu actions for suggestion/agent model switching.
    - Offer local/cloud mode toggles and sign-in/sign-out actions.
    - Offer a Cloud maintenance action to check local models in-place and show
      its progress inside a modal dialog.
    - Append user prompts and Ollama responses to the output pane.
    - Keep the prompt box multiline so Shift+Enter can insert a newline.
    - Clear the prompt immediately when Send is pressed.
    - Persist the AI preferences through the existing profile store.
    - Provide bordered, syntax-highlighted code boxes for fenced blocks and a
      right-click Copy answer command for the whole rendered response.
    - Keep the rendered answer streaming live through the markdown renderer
      while reply chunks arrive, so special characters and code blocks remain
      readable incrementally instead of waiting for the final pass.
    - Keep the code-cell selection/copy affordance and reply formatting
      separate so the live stream can stay incremental while the renderer still
      owns the final look.
    - Keep the answer host autoscrolling the live stream without flicker while
      the chunks arrive, so the current query stays above the rendered answer
      blocks in one continuous page.
    - After the final markdown render, scroll the answer pane back to the top
      so the rendered response starts at its first line instead of staying at
      the bottom.
    - The answer host no longer creates a native WS_VSCROLL bar. The inner
      answer RichEdit fills the host and carries the custom MSB scrollbar
      (msb_attach) on its right edge, so the custom bar is the only vertical
      scrollbar on the pane.
    - Current status: the full answer now renders (query, prose, and every
      code block); each code box is syntax highlighted and copyable on its own,
      and the pane scrolls with the custom MSB bar.
    - Keep the timer/status line split so the live elapsed timer stays on the
      right and the cloud / sign-in / model info stays on the left.
    - Restore the owner/main window to the foreground on close with the brief
      TOPMOST trick, then immediately remove the pin so it does not stay on top.

  Text wrapping:
    - Both RichEdit panes are created without horizontal scrolling.
    - EM_SETTARGETDEVICE(NULL, 0) is applied so each pane wraps to its current
      control width.
    - WM_SIZE reapplies the wrap target after the controls are resized.

  Reply rendering:
    - The reply parser normalises model escape text like u003c/u003e before
      it reaches RichEdit so sample HTML-like spans do not print literally.
    - Reply text is repainted live through the markdown renderer while the
      Ollama stream is still arriving.
    - Incoming chunks also feed the incremental live formatter so styled code
      blocks can appear before completion.
    - Fenced code blocks render in a bordered box with Scintilla/Lexilla
      syntax highlighting (NsbAi_HighlightCode, mapped from the fence
      language) and are tracked by character range. Double-click or Ctrl+A
      selects just that block's code, Ctrl+C copies it without the empty
      padding lines, and a right-click Copy menu copies the selection (or the
      whole cell when nothing is selected).

================================================================================
2. ENTRY POINT
================================================================================

  void Ne_ShowAiWindow(HWND parent)

  Behaviour:
    - Reuses the existing AI window if it is already open.
    - Registers the NSBEditAIWindow class on first use.
    - Centers the window over the parent when possible.
    - Creates a WS_OVERLAPPEDWINDOW top-level window with modal-frame styling.
    - Calls ShowWindow / UpdateWindow / SetForegroundWindow after creation.

================================================================================
3. WINDOW STATE
================================================================================

  AiWindowState stores the runtime state for the window:
    - hHeader, hLog, hInput, hStatus
    - hSendBtn, hCopyBtn, hClearBtn, hCloseBtn
    - hFont, hPaneFont
    - dd (owner-draw button spec block)
    - model, fallback
    - cloudModel (selected Ollama cloud model, e.g. qwen3-coder:480b-cloud)
    - cloudMode, signedIn

  The state object is allocated before CreateWindowExW and attached through
  WM_CREATE via GWLP_USERDATA. It is released on WM_DESTROY.

================================================================================
4. BOOTSTRAP AND PREFS
================================================================================

  Bootstrap defaults come from NeAiBootstrap_Get():
      - model defaults to qwen3-coder
    - fallback defaults to qwen2.5-coder:3b

    If older saved prefs still contain qwen2.5-coder:7b-instruct,
    qwen2.5-coder:7b, or qwen2.5-coder, Ai_LoadPrefs() normalises them back to
    qwen3-coder on startup so installed builds self-heal.

  Saved preferences are loaded in Ai_LoadPrefs() and written back by
  Ai_SavePrefs() using NeProfiles_SetStrSetting / NeProfiles_SetIntSetting.

  Persisted keys:
    - ai.model
    - ai.fallback
    - ai.cloud_model
    - ai.cloud_mode
    - ai.signed_in
    - ai.cloud_api_key   (ENCRYPTED via NeProfiles_SetSecretSetting/GetSecretSetting;
                          AES-256-CBC NeCrypto, DPAPI-wrapped key, stored as hex —
                          never plaintext.  Loaded key is pushed to the client with
                          NeAiClient_SetCloudApiKey so cloud sends can use it.)

  CLOUD SIGN-IN (two paths)
    (a) Local daemon (browser connect): `ollama signin` links this machine's key
        to the account; ai.signed_in is only a cache, reconciled from POST
        /api/me (200 signed in / 401 signed out) on window open and reuse.
    (b) API key (browser-free): Cloud -> Add API key (IDM_AI_SET_API_KEY) opens a
        masked Ne_ShowInputDialog; the key is validated with
        NeAiClient_ValidateCloudApiKey (GET https://ollama.com/api/tags, bearer)
        and stored encrypted.  With a key set, Ai_ReconcileSignInState uses the
        key's validity as the sign-in state and does NOT switch to a local model.
        The "-cloud" send is routed by NeAiClient_AskOllamaStream to
        https://ollama.com/api/generate over WinHTTP (WINHTTP_FLAG_SECURE +
        Authorization: Bearer) via Ai_CloudAskStream — curl is not used because
        the bundled curl has no CA bundle.  A WM_MENUSELECT handler shows a
        dedicated AI-owned tooltip (Ai_ShowMenuTip/Ai_HideMenuTip, s_hAiTipWnd)
        for the menu item (AI_TIP_ADD_API_KEY, literal \n -> newline).  It does
        NOT use the shared tooltip.cpp singleton: that window is owned by the
        first top-level window to show a tooltip (the editor), so showing it from
        the separate AI window pulled the editor forward and sent the AI window
        behind.  The dedicated tooltip (same yellow COLOR_INFOBK look, 12pt Segoe
        UI bold, WS_EX_NOACTIVATE) is owned by the AI window and never steals
        activation; it is destroyed in WM_DESTROY (Ai_DestroyMenuTip).

  MENU FONT GOTCHA
    The owner-draw menu font s_hAiMenuFont is a file-scope global.  It is created
    lazily in WM_MEASUREITEM/WM_DRAWITEM and freed on WM_DESTROY.  DeleteObject
    MUST be followed by `s_hAiMenuFont = NULL`, otherwise the next time the AI
    window opens `if (!s_hAiMenuFont)` is false, the dangling handle is reused,
    SelectObject fails, and the menu falls back to the tiny default system font
    (intermittently, depending on GDI handle reuse).

  SIGN-IN DETECTION (ai.signed_in is only a cache)
    ai.signed_in is NOT authoritative — Ollama tracks sign-in via the CLI
    (`ollama signin` / `ollama signout`), and the user can sign out from a
    terminal while NSBEdit is closed, leaving the stored flag stale (window
    would wrongly show "Account: signed in" with Cloud models enabled).
    The real state comes from the local daemon:
        POST http://localhost:11434/api/me
          HTTP 200        -> signed in
          HTTP 401 / 403  -> signed out
          other / no daemon -> unknown
    There is NO GET whoami endpoint (GET /api/me returns 405).
    NeAiClient_QueryOllamaSignIn() (ne_ai_client.cpp) performs this probe and
    returns a tri-state int: 1 signed in, 0 signed out, -1 unknown (4 s
    WinHttpSetTimeouts so window-open never stalls when offline).
    Ai_ReconcileSignInState(st) (ollama_ai.cpp) adopts the live value and
    rewrites ai.signed_in ONLY when the answer is definitive (>= 0); on -1 it
    keeps the cached value.  It runs at window open (inside Ai_LoadPrefs, BEFORE
    Ai_LoadHistory so it must persist single keys directly, NOT via Ai_SavePrefs
    which would clobber history) and again on the Ne_ShowAiWindow reuse path.
    When the daemon reports signed-out it also forces local mode: sets
    st->cloudMode = false, persists ai.cloud_mode = 0, and picks a local model —
    the last-used one (st->model) if still present in Ai_GetModelCandidates(),
    otherwise the first entry in that list (Ai_DefaultModelName() if the daemon
    list is empty) — persisting ai.model.  This keeps the user off a greyed-out
    cloud model after an external signout.

  CLOUD MODE (how it works)
    Ollama cloud models are served through the SAME local endpoint
    (localhost:11434 /api/generate) once the user has run `ollama signin`; the
    local daemon proxies `-cloud` models to Ollama's cloud.  So cloud mode is
    NOT a separate transport: Ai_DoSend routes cloud sends through the normal
    Ai_BeginBusyState + Ai_StartSendWorker path using st->cloudModel, which is
    why the Stop button and the spinner work identically to local.  No local
    fallback model is used in cloud mode (a cloud error is surfaced instead).
    The Model menu lists a curated set of cloud models plus any "cloud" models
    the local daemon reports (Ai_CloudModelCandidates), greyed until signedIn,
    under greyed "Local:" / "Cloud" section headers (AI_MENU_LOCAL_HEADER /
    AI_MENU_CLOUD_HEADER).

  REASONING MODELS / DOUBLING
    Cloud reasoning models (qwen3-coder, gpt-oss, deepseek) stream a `thinking`
    field alongside `response`.  Ai_OllamaWriteCallback (ne_ai_client.cpp) must
    append the answer from `response` and use `thinking` ONLY as a fallback when
    a line has no `response` — otherwise every token is emitted twice (both
    fields fire onChunk), duplicating the answer and corrupting ``` code fences.

  COMPLETION RACE
    Live typing is pumped from st->liveTypingQueue on a timer.  On a fast reply
    WM_AI_SEND_COMPLETE can arrive while the queue is only partially pumped, so
    the final render must adopt the worker's COMPLETE result->reply, clear the
    queue and stop the typing timer before Ai_RenderMarkdownReply — otherwise a
    code block is cut mid-line and its tail is appended as raw text below the
    code cell (and is not copyable).

  No raw-reply debug file is written in release builds (Ai_WriteRawReplyFile is
  a no-op).

  The bootstrap reader is intentionally separate so the AI shell can fall back
  to a safe default even if the profile store is empty.

5. MENU MODEL
================================================================================

  The AI window uses a simple menu bar with four submenus:
    - Model
    - Cloud
    - Log
    - Help

  Model submenu:
    - Suggestion: default model
    - Agent: fallback model

  Cloud submenu:
    - Local only
    - Cloud subscription
    - Sign in to Ollama
    - Sign out
    - Open Ollama web site

  Log submenu:
    - Send prompt
    - Clear log
    - Copy answer

  Help submenu:
    - About this window

  Ai_RefreshUi() keeps the checkmarks and status text in sync with the stored
  state after every menu change.

================================================================================
6. LAYOUT AND DRAWING
================================================================================

  The layout is a fixed client-size dialog-style arrangement:
    - header/status summary at the top
    - multiline prompt editor taking roughly one third of the body
    - centered owner-draw action row directly under the prompt editor
    - multiline read-only answer pane taking the remaining space
    - status line pinned to the bottom

  Current geometry is DPI-scaled through S(). Button widths are measured with
  Ai_MeasureButtonWidth() so the label text and icon always fit. The answer
  pane uses a monospace font so fenced code blocks and indentation remain easy
  to read.

  The Ollama icon is loaded from ollama.png in the executable directory, not
  from the current working directory. That keeps the icon visible after install
  and when the app is launched through a shortcut.

  Owner-draw buttons use Ai_DrawButton():
    - Green for Send
    - Blue for Copy, with a clipboard-style glyph
    - Red for Clear
    - Red for Close

  Only the Send button uses the Ollama image; Copy uses the clipboard glyph,
  and Clear/Close are plain text buttons.

  The button spec is stored in AiDialogData so WM_DRAWITEM can paint the
  current button set without hardcoded text comparisons.

  Known layout issue:
    - Some button and field placements can overlap when the window is reduced.
    - That should be fixed before more AI UI elements are added.

================================================================================
7. MESSAGE FLOW
================================================================================

  WM_CREATE
    - Restores settings.
    - Builds the menu.
    - Creates the header, prompt editor, answer pane, buttons, and status line.
    - Applies the common 12pt dialog font to chrome and a monospace pane font
      to the text areas.
    - Populates the initial status text and opens the answer pane with a
      startup line.

  WM_SIZE
    - Repositions all child controls.
    - Keeps the prompt editor around one third of the body height.
    - Centers the action row under the prompt editor.
    - Lets the answer pane use the remaining space.

  WM_COMMAND
    - Handles model/cloud/sign-in/log/help commands.
    - Send triggers Ai_DoSend().
    - Copy, Clear, and Close are also routed from their owner-draw buttons.
    - Copy answer uses the rendered answer range, not the whole log buffer.

  WM_CONTEXTMENU
    - Right-click on the answer pane opens a small popup menu with Copy.
    - That menu calls the same answer-copy path as the Log submenu and Copy
      button.

  WM_DRAWITEM
    - Paints the owner-draw buttons through Ai_DrawButton().

  WM_CTLCOLORSTATIC / WM_CTLCOLOREDIT
    - Uses normal window colors for the edit/static controls.

  WM_DESTROY
    - Deletes the font.
    - Releases the state block.
    - Clears the global window handle.

================================================================================
8. SEND BEHAVIOUR
================================================================================

  Ai_DoSend() now sends the current prompt to Ollama on localhost on a worker
  thread and returns immediately to the UI.

  Cloud login gate:
    - If cloudMode is true and signedIn is false, Ai_DoSend() opens the Ollama
      sign-up page and returns immediately.
    - That keeps the local transport path isolated from the sign-in redirect.
    - Real cloud request handling stays a separate follow-up slice.

  Current request path:
    - curl POST http://127.0.0.1:11434/api/generate
    - send the selected model and prompt as JSON
    - stream the response through the curl write callback and post each chunk
      back to the window as soon as it is parsed

  Before sending, the AI window prefixes a short markdown instruction so code
  answers are more likely to come back fenced and indentation-safe.

  The output pane shows the user's question first, then the Ollama reply or a
  short error message if the local service is not reachable.
  The answer path is now incremental all the way from curl to the live typing
  queue, so the visible response starts writing as soon as the first chunks
  land.

Project suggestion mode (v2026.07.06.11)
----------------------------------------
  - Project store: ne_projects.h/.cpp. Reuses the ne_profiles SQLite handle;
    `projects` table (id/name/root_path) + settings key `active_project`
    (0 = none, survives restart). NeProjects_CollectFiles walks the root and
    FOLLOWS symlinks/junctions (reparse points), cycle-guarded by canonical
    paths (GetFinalPathNameByHandleW); Prj_SkipDir skips heavy dirs and
    Prj_SkipFile skips *.log / build*.txt / makeit*.log / output.txt / ai*.txt
    so stale build logs never enter AI context.
  - Context build runs on the UI THREAD before the send worker, because the
    SQLite handle is single-threaded (THREADSAFE=0). Ai_BuildProjectContext
    prepends a bounded "[PROJECT CONTEXT - SUGGESTION MODE]" block: rules
    (answer directly, ignore logs, name exact file+location), a small file
    listing (80), grep snippets, then the exact named files LAST (llama.cpp
    keeps the tail on truncation).
  - Named-file resolution: Ai_ExtractFileRefs pulls path/ext-looking tokens;
    Ai_ResolveRef resolves exact then fuzzy. Path-qualified names go through
    Ai_ResolveOnDisk (segment-by-segment edit-distance match against real
    directory entries, so ".\;yStyle\API_list.txt" -> MyStyle/API_list.txt and
    junctions are traversed); bare names match collected files by base name.
    Corrections are reported to the model.
  - Code search: Ai_ExtractSearchTerms (backtick spans + identifier/camelCase),
    Ai_SearchSnippets greps files and emits matching lines with context (6
    before / 34 after) so a function is captured without the whole file. When
    snippets are found they REPLACE the broad whole-file dump.
  - Big files: Ai_PlanBigFileChunks - a named file > 12000 wchars with NO
    matching search term is split into 8000-wchar batches. Ai_StartSendWorker
    gained mapChunks/reduceHeader: each batch is analysed via non-streamed
    NeAiClient_AskOllama, notes collected, then the reduce prompt is streamed as
    the answer. Progress via WM_AI_PROGRESS (WM_APP+75) -> spinner->SetText.
  - Responsiveness: ne_ai_client sets options.num_ctx=12288; prompt budgets are
    small (listing 80, content total 12000 wchars). Prompt size drives local
    prefill time - a 188KB file (~47k tokens) stalled for minutes before this.
  - Spinner progress: kAiThinkingTimerId (1s) calls Ai_UpdateSpinnerProgress ->
    best-guess pct = 95*e/(e+25); gated by st->chunkedActive so it does not
    fight real batch progress. Spinner hides on the first streamed chunk.
  - Rendering: Ai_ParseAnswerBlocks always keeps raw markdown now; the fixed
    inline renderer (Ai_AppendMarkupLine) handles **bold**, *italic*, `code`
    (Consolas box), #..###### headings, "> " quotes and "- "/"+ " bullets. All
    inline CHARFORMAT masks include CFM_BOLD|CFM_ITALIC so effects never leak.
  - Model menu: Agent entries removed (Suggest-only public build); the
    AiMenuRole enum/infra stays for a future Agent return.

v2026.08.01.08 - Query-box paste (Ctrl+V) safety + no multi-line prompt truncation
  - Ai_InputSubclassProc already had a safe WM_PASTE branch: it reads CF_UNICODETEXT
    (or CF_TEXT) itself, sanitizes the buffer (drop NUL, collapse CRLF/CR/LF to the
    single CR that RichEdit uses internally, and drop other C0 control chars except
    TAB), inserts with EM_REPLACESEL, then forces the pasted run to solid black via
    EM_SETCHARFORMAT (CFM_COLOR). This avoids EM_PASTESPECIAL, which crashes the
    control on some console (CMD/PowerShell) multi-line payloads, and keeps text
    readable when it was copied from a dark editor tab.
  - BUG (fixed): that handler was BYPASSED by Ctrl+V. RichEdit's built-in Ctrl+V
    pastes the clipboard's rich content directly without routing through the
    subclass WM_PASTE, so:
      * text copied from a dark editor tab kept its light colour -> nearly invisible
        on the white query box, and
      * console payloads went through RichEdit's own (crashy) paste and corrupted
        the control -> the app crashed a moment later, typically on the next Send
        (classic deferred heap-corruption symptom).
    Only the right-click Paste worked, because it does SendMessage(WM_PASTE).
  - FIX: intercept the keystroke in Ai_InputSubclassProc WM_KEYDOWN - Ctrl+V (V with
    VK_CONTROL down, VK_MENU up to leave AltGr alone) and Shift+Insert - call
    SendMessage(hwnd, WM_PASTE, 0, 0) and return 0 to swallow the key, plus swallow
    the Ctrl+V WM_CHAR 0x16, so the safe path runs EXACTLY ONCE (no double paste).
    Lesson: never rely on a subclass WM_PASTE alone for a RichEdit - Ctrl+V may not
    route through it; trap the key (or handle EM_PASTESPECIAL) explicitly.
  - BUG (fixed): multi-line prompt truncated on Send. Ai_DoSend / Ai_HistoryBrowse
    read the input with GetWindowTextW(buf, inLen+1) where inLen = GetWindowTextLengthW.
    RichEdit reports the length with single-CR line breaks but GetWindowText emits
    CRLF, so a multi-line prompt overflowed inLen+1 and was cut off. Buffer is now
    sized inLen*2+2 (worst-case CRLF expansion) and resized to the returned count.
