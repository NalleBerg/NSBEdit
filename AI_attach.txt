NSBEdit AI attachment rule book
//
// This file is the reference for how the AI attaches to the editor.
// It is meant to be read by a person and written mostly by the GUI.
// The GUI should present the normal choices through menus and buttons.
// The file must still remain editable by hand so the user understands what
// the AI is allowed to do.
//
// The important rule: NSBEdit is the controller.
// - NSBEdit chooses the work root.
// - NSBEdit reads files, searches files, writes files, runs tools, and applies
//   patches.
// - The AI dialog is the front end.
// - The AI dialog shows the prompt, reply, mode, permission state, diffs, and
//   build results.
// - The AI itself does not get direct unrestricted access to the file system.
// - Every read, search, write, and run action is mediated by NSBEdit.
//
// Project handling:
// - The user selects one work root.
// - The work root includes the root folder itself and all folders below it.
// - The GUI may also offer narrower project scopes later, but the first model
//   should be root-first and subtree-wide.
// - The selected root is the boundary for all permissions unless a rule book
//   entry explicitly says otherwise.
// - The GUI should show the current root clearly before the AI reads anything.
//
// Read / search / write / run model:
// - read = load one file or many files into AI context.
// - search = scan multiple files for text, symbols, names, or patterns.
// - write = create, replace, patch, or update files.
// - run = execute scripts, build steps, or validation tools.
// - Suggest mode uses read + search only.
// - Agent mode may use read + search + write + run if the rule book allows it.
// - NSBEdit, not the model, decides whether an action is permitted.
//
// Mode overview:
// - [Blocked]
//   * no read
//   * no search
//   * no write
//   * no run
// - [Full access]
//   * read, search, write, and multi-file updates are allowed
//   * run is still separate and should only happen if run access is also set
// - [This session]
//   * same practical access as Full access
//   * expires when the session is idle for more than one hour
//   * the GUI should track the last AI activity time and clear the grant on timeout
// - [Run access]
//   * execution only
//   * scripts, make/build steps, and validation commands are allowed
//   * write permission does not automatically follow
//
// GUI mapping:
// - Block -> [Blocked]
// - Allow -> [Full access]
// - Allow for this session -> [This session]
// - Allow run -> [Run access]
// - The GUI should write these rules through a simple Allow ▼ control.
// - The GUI should show the effective result before it performs anything risky.
//
// Time handling:
// - [This session] must be tied to a timer.
// - Any AI read, search, reply, approval, write, or run should refresh the timer.
// - If the session sits idle for more than one hour, temporary permission expires.
// - After expiry, the GUI should fall back to the permanent rules.
//
// Attachment workflow:
// - The GUI gathers context from the editor.
// - The GUI reads the root rule book.
// - The GUI shows the user what the AI may see.
// - The AI receives only the files and snippets that NSBEdit decided to send.
// - The AI may suggest changes, but NSBEdit applies them.
// - For agent mode, NSBEdit must show the change set or diff before it writes.
// - For suggest mode, NSBEdit must not write automatically.
// - For run access, NSBEdit must show the command and the target before launch.
//
// Conflict handling:
// - The GUI computes the effective result from the rule book.
// - A narrow explicit allow rule may override a broader blocked folder when the
//   allow rule is more specific to the same path.
// - If two rules conflict, the GUI should show the conflict clearly.
// - The safer answer should win unless the user explicitly overrides it.
// - The user should always be able to see why a path is blocked or allowed.
//
// Regex rules:
// - Every rule below is a regex pattern.
// - Use ^ and $ when you want exact folder or file boundaries.
// - Use [\\/] so the same rule works on Windows paths with either slash type.
// - Use (?:...) for non-capturing groups.
// - Keep the patterns readable.
// - The GUI should be able to generate the common presets safely.
//
// Presets the GUI can create:
// - Block folder
// - Allow folder
// - Allow subtree
// - Allow single file
// - Allow run-only script
// - Allow only for this session
// - Custom regex
//
// How the rule book should be used:
// - The GUI owns the common actions.
// - The user can still open and edit the file directly.
// - The file should be self-explaining, not hidden behind the GUI.
// - NSBEdit should never treat access as global just because the dialog is open.
// - The selected root, mode, and effective permission should be visible at all times.
//
// Examples below are regex patterns relative to the work root.

[Blocked]
^SetupCraft(?:[\\/]|$)                         // Block the SetupCraft subtree by default.
^backup_current_ai(?:[\\/]|$)                  // Block scratch AI backup folders.
^.*[\\/]private(?:[\\/]|$)                   // Example: block any private subtree.
^.*[\\/]secrets(?:[\\/]|$)                   // Example: block secret or credential folders.

[Full access]
^$                                              // The work root itself.
^MyStyle(?:[\\/]|$)                           // Allow the shared style / docs tree.
^SetupCraft[\\/]SetupCraft(?:[\\/]|$)       // Explicit exception inside a blocked area.
^ollama_ai\.cpp$                               // Example: allow the AI shell implementation file.
^AI_attach\.txt$                                // Example: allow editing the attachment rule book itself.

[This session]
^Sandbox(?:[\\/]|$)                            // Temporary access while the session is active.
^TempAI(?:[\\/]|$)                             // Example session-only working area.
^.*[\\/]scratch(?:[\\/]|$)                   // Example: temporary scratch workspace.
^.*[\\/]experiments(?:[\\/]|$)               // Example: short-lived experimental files.

[Run access]
^(?:.*[\\/])?makeit\.bat$                     // Allow makeit.bat in any folder under the work root.
^(?:.*[\\/])?pack\.ps1$                       // Allow pack.ps1 in any folder under the work root.
^(?:.*[\\/])?NewVersion\.ps1$                 // Allow the version-stamping script anywhere under the work root.
^(?:.*[\\/])?[^\\/]+\.ps1$                  // Allow a PowerShell script when the GUI marks it runnable.
^(?:.*[\\/])?[^\\/]+\.cmd$                  // Allow a command script when the GUI marks it runnable.
^(?:.*[\\/])?[^\\/]+\.bat$                  // Allow a batch file when the GUI marks it runnable.

// Practical examples:
// - ^SetupCraft(?:[\\/]|$) blocks the whole SetupCraft tree.
// - ^SetupCraft[\\/]SetupCraft(?:[\\/]|$) re-opens one specific folder inside
//   that blocked tree.
// - ^$ matches the work root itself.
// - ^.*makeit\.bat$ lets the GUI run makeit.bat in any folder under the root.
// - ^.*[\\/]experiments(?:[\\/]|$) is a session-only temp area that expires
//   after one hour of idle time if the GUI is tracking the timer correctly.
// - ^.*[\\/]secrets(?:[\\/]|$) is the kind of path that should stay blocked
//   even if a broader allow rule exists somewhere else.

// Final notes:
// - The file should stay readable by the user.
// - The GUI should own the common actions, but the rule book must still be
//   understandable and editable by hand.
// - The AI must never treat access as global just because the editor is open.
// - The effective result should always be shown back to the user before the AI
//   reads, writes, searches, or runs anything important.
