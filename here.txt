THE REGRESSION (THE "serious error" — NOT fixed)
- SYMPTOM: cloud sends (even text-only, e.g. "show me tiny c++ code") take
  minutes (observed 6:41) in THIS build. The SAME query on the last good
  milestone answers in ~2 s.
- CONFIRMED baseline: milestone v2026.10.03.09 "Edition/Utgave 4"
  (published 03.10.2026 09:59) = ~2 s cloud reply. That is the known-good.
- The cache-first change to the cloud caps worker (query only uncached
  models) did NOT fix it — still slow after that edit.
- LEADING HYPOTHESIS: the new cloud vision-capability probe
  (Ai_RefreshCloudCapsAsync -> NeAiClient_QueryCloudModelVision, ollama.com
  /api/show) still contends with / throttles the user's cloud send. Each
  call opens its OWN WinHTTP session with WINHTTP_ACCESS_TYPE_DEFAULT_PROXY
  (per-session proxy/WPAD resolution). On a FRESH install the cache is empty
  so the first window-open fires ~18 of these, racing the first send.
- THINGS TO TRY NEXT (in order):
  1. Make cloud caps FULLY LAZY: query a cloud model's vision only when it
     is hovered/selected (WM_MENUSELECT), zero background burst. Simplest
     safe fix; cloud markers fill in on first hover.
  2. Reuse ONE WinHTTP session for all caps probes (avoid 18x proxy/TLS).
  3. Delay the caps probe well after open AND skip while a send is active
     (gate on Ai_BeginBusyState / a g_aiSendActive flag).
  4. If still slow, TEMPORARILY disable Ai_RefreshCloudCapsAsync entirely
     (fall back to the name heuristic for cloud markers) and re-measure to
     PROVE the probe is the cause before investing more.
  5. Confirm it is NOT the project-context build (Ai_BuildProjectContext,
     "Searched NNNN files") or chunked map-reduce being wrongly triggered
     (spinner showing a climbing %). Compare request body size vs the good
     milestone.
