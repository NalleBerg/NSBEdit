THE OPEN PROBLEM -- LAG on every send (NOT fixed)
- SYMPTOM: even a simple code question ("Give me the code to a win32 window
  with only Exit on the menu bar") took ~35 s before answering (spinner reached
  ~58% on the fake curve = ~39 s). Also affects non-image queries.
- ROOT CAUSE: the autonomous web-search ROUTER I added this session makes an
  EXTRA LLM call per send to decide whether to search. In CLOUD mode it runs on
  the CLOUD model (work.fallback is empty in cloud) -> a second cloud
  round-trip before the answer. Measured: a LOCAL qwen2.5-coder:3b router took
  13.8 s cold. Two LLM calls (router + answer) ~= the 35 s.
- Code: ollama_ai.cpp
    * Ai_RouterWebQuery(model, userQuestion)  ~ lines 3719-3759  (the LLM call)
    * worker "Autonomous web retrieval" block  ~ lines 3945-3972  (calls it)
    * Ai_ExtractWebQuery(prompt)  ~ line 4799+  (explicit keyword heuristic,
      UI thread, used by the explicit/toggle path)

PLANNED FIX (DONE last session -- router removed, heuristic expanded)
- Remove the per-query LLM router; detect "needs web" with an INSTANT keyword
  heuristic instead (no extra model call):
    1. DELETE Ai_RouterWebQuery (note: -Wall warns on an unused static function,
       so it MUST be removed when its only caller is removed).
    2. DELETE the worker "Autonomous web retrieval" block that calls it.
    3. EXPAND Ai_ExtractWebQuery signals with recency/currency terms so the
       EXISTING explicit path fires autonomously too: e.g. "recent", "recently",
       "latest", "newest", "nowadays", "these days", "this year", "this month",
       "today", "news", "announced", "2024","2025","2026","2027", "currently".
       Keep them NON-code terms to avoid false positives (do NOT add "api",
       "code", "function", bare "update").
  Result: simple code questions have NO web signal -> no search -> fast.
  "any recent updates on Ollama API?" -> "recent" -> searches. Explicit
  "search the web ..." and the Log toggle still work. webBlock is still built
  via Ai_FormatWebResultsBlock (grounding instruction) which stays.
- OPTIONAL follow-ups if the heuristic feels too narrow: run the search in the
  worker (non-blocking) using the heuristic query, or bring back a SMART router
  but only when a cheap pre-filter flags possible need AND run it on the already
  warm answer model.
