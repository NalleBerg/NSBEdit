 OPEN DECISION (can be changed later without reworking the steps)
-------------------------------------------------------------------------------
 What build system do GENERATED projects use?
   DEFAULT CHOSEN HERE: generate BOTH per project —
     - a per-project makeit.bat  (the canonical build_command; mirrors NSBEdit's
       clean MinGW/windres/g++ flow so every project feels the same), AND
     - a CMakeLists.txt          (for IDE/portability; optional to use).
   build_command for a new project defaults to its generated makeit.bat.
   NSBEdit itself keeps its own existing makeit.bat unchanged.
 If you later prefer CMake-only (build_command = "cmake --build build"), only the
 template contents + the default build_command change; the step structure holds.

[x] STEP 1 — Extend the projects table (invisible, backward compatible)  DONE 2026-09-05
    (cols type/build_command/run_command in CREATE TABLE + guarded ALTER in
     NeProjects_Init; makeit.bat seed for makeit-style roots; runs every launch
     incl. USB/portable. Build OK.)
    - ne_projects: add columns type, build_command, run_command to the projects
      table via a safe migration (ALTER TABLE ... ADD COLUMN if missing; existing
      rows get sensible defaults). NULL/empty => treat as "unset".
    - Seed the NSBEdit project's build_command = "makeit.bat" (only if that row
      exists / matches this workspace root).
    - PORTABLE / FRESH DB: the DB is created at init on EVERY launch via
      CREATE TABLE IF NOT EXISTS (NeProfiles_Init / NeProjects_Init), and the DB is
      the shared %APPDATA%\NSBEdit\nsbedit.db for BOTH installed and portable runs
      (portable exe-dir db is migrated up on first run). So we never ship a pre-
      built DB. BUT: CREATE TABLE IF NOT EXISTS does NOT add columns to a table an
      older DB already has. So do BOTH:
        (a) put the new columns in the CREATE TABLE (fresh/portable DBs get them),
        (b) run guarded ALTER TABLE ADD COLUMN for already-existing DBs (ignore the
            "duplicate column" error, or check pragma table_info first).
      Same pattern later for the `language` column (Phase E) and the agent_edits /
      agent_edit_files tables (those are plain CREATE TABLE IF NOT EXISTS — fine).
    - USB / TRULY-PORTABLE FIRST RUN: on a PC with the app NOT installed, the DB
      falls through to the last-resort branch and is created BESIDE THE EXE (on the
      USB stick), because AppData has nothing yet and it isn't running from Program
      Files (Np_GetDbPath). When that stick is later used next to an installed exe,
      Np_CopyDbToAppData migrates it UP to AppData — so the USB DB becomes the
      developer's real DB. THEREFORE the New Project schema MUST live in
      NeProjects_Init (which runs at startup on EVERY launch + EVERY location,
      right after sqlite3_open), so the USB DB contains the New Project tables from
      first creation. The guarded ALTERs running every launch also auto-upgrade a
      USB DB made by an older exe. Do NOT put schema creation in any UI-only/lazy
      path a portable first run could skip.
    - No UI change. Build + run. Commit.

 DESIGN NOTES / OPEN QUESTIONS
 - LANGUAGE is a separate axis from project KIND. The dialog needs a Language
   selector; the Type/Kind list + Build command default + scaffold files all
   DEPEND on the language:
       C++    -> CLI / Windows GUI / DB        (build: makeit.bat / cmake)
       C      -> CLI                            (build: makeit.bat / cmake)
       Python -> CLI / script                   (no compile; run_command = python)
       HTML   -> Website (static)               (no build)
       PHP    -> Website (server)               (no local build; needs a server)
       (extensible — don't hardcode a closed set)
 - New projects table columns likely need: language (+ reuse type/build_command/
   run_command from Step 1). Add via the same safe migration.
 - LOCATION axis: web languages (HTML/PHP) must be creatable ONLINE, directly on
   an FTP server, NOT only in a local empty folder. So the dialog's "where" needs
   a mode:
       LOCAL folder (current Step 3 flow), OR
       REMOTE/FTP target (reuse the existing FTP support: ne_ftp.*, the FTP menu,
       stored FTP profiles). Scaffold files are written to the server via FTP.
 - The "empty folder" rule maps to "empty remote dir" for FTP projects (refuse a
   non-empty remote target too).
 - PROFILE GAP: the target FTP site may be one we have NO profile for yet. So
   creating an FTP project may need to add a new FTP profile as part of the flow.
   Options: (a) inline "Add FTP profile..." in the New Project dialog, or
   (b) jump to the existing FTP profile manager to add/choose one (it already has
   an Add). Prefer (b) to reuse existing UI; return to New Project with the chosen
   profile selected.
 - Templates per web language: HTML -> index.html + style.css + script.js; PHP ->
   index.php + a small include + .htaccess; both get README/CHANGELOG locally or
   remotely as appropriate.
